  Built the simple version instead:
  - **`pull_source()`** — `install` and `update` now `git pull --ff-only` the checkout before copying anything. This was a genuine footgun: a stale checkout installed stale content and reported success. Non-fatal on every irregular state (not a git checkout, uncommitted changes, detached HEAD, no upstream, offline) — it says what it found and proceeds with the files on disk. `WAYPOINT_NO_PULL=1` opts out.
  - **`.waypoint/VERSION`** — stamps the source commit at install and update. The version *is* the commit, so it cannot drift from the content the way a hand-maintained number would. This is most of CONOPS §8.4 without a release process.
  - **`report_changes()`** — `update` runs `git log <stamped>..HEAD -- skills templates adapters` and prints what you're crossing, flagging when `templates/opord.md` is in the range since that is the one file `update` refuses to touch. Handles an unrecognised stamp (installed from a different clone) without failing.
  - **`test.sh`** — 52 assertions. Covers what `update` promises not to touch (extended OPORD, user-authored skills, a written CONOPS), that it *does* restore edited core skills, the scaffold lifecycle, both migration paths, the install guards, spaced paths, and the unknown-revision case. All passing.

  Design consequence worth remembering: making `update` pull is what forced `WAYPOINT_NO_PULL` to exist, because the tests cannot be allowed to mutate the developer's own checkout. The flag then turned out to be what offline users want too.
